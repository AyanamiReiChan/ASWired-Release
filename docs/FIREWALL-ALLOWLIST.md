# 业务端口 IP 白名单

v1.0.16 新增由管理 Agent 执行的业务端口来源 IP 白名单。管理员在服务器页面打开“端口访问控制”，选择服务器及受管入站端口，填写客户前置节点的固定出口 IP 后保存并应用。只有任务执行成功、Agent 实际核验结果与当前策略一致时才显示已应用。

## 部署条件

- 主控和网站升级至 v1.0.16 后，还需要把目标服务器的 **ASWired 管理 Agent** 升级至 v1.0.16；Komari 探针不能代替管理 Agent 执行防火墙操作。
- 首版面向 Linux 原生部署，需要 nftables、相应网络管理权限，以及可识别的本机原生 Xray 业务监听端口。网站仅提供受管 VLESS TCP REALITY 入站端口。
- 首次应用前须先发布入站，并确认其已在该 Agent 中运行。首版支持 `0.0.0.0` 或 `::` 通配监听；自定义单 IP 绑定、重复端口、SSH 和 Agent 管理端口不在可选范围内。
- Agent 不会自动安装系统软件。Debian/Ubuntu 缺少 nftables 时，由管理员安装相应软件包，再读取实际状态；无需开启会重载全机规则的 nftables 服务来使用此功能。
- 原有主机防火墙或商家安全组仍然有效。列入 ASWired 白名单只代表通过这层限制，不能覆盖其他防火墙的拒绝规则。

## 客户链式代理示例

链路为“客户设备 → 客户前置服务器 → KDDI → 目标网站”时，KDDI 看到的是前置服务器的公网出口 IP。填写该 IP，例如文档示例地址 `203.0.113.10/32`，并给客户独立订阅凭据；IP 白名单不会替代 UUID 等代理认证。

建议为客户建立专用入站和端口，并仅将该节点分配给对应套餐或订阅实例。多个客户共用同一端口时，该端口使用共同的 IP 允许列表；需要独立的 IP 访问范围时使用不同端口。

“订阅白名单”只控制订阅下载；“在线 IP 上限”只控制同时在线 IP 数量。它们不能替代这里的实际端口来源限制。

## 设置及结果

1. 在服务器页面打开“端口访问控制”，选定目标服务器。
2. 添加规则，选择已有业务端口，填写名称及允许的 IPv4/IPv6 IP 或 CIDR。单个 IPv4 等价于 `/32`，单个 IPv6 等价于 `/128`。至少填写一个地址；空列表不会被当成“允许全部”。
3. 点击“保存并应用”，等待对应任务结束，再核对实际状态和检查时间。
4. 从允许的出口 IP 与另一个未允许的出口分别验证连接。只有 IPv4 地址的列表不会自动允许 IPv6 来源。

页面上的规则是主控保存的期望配置，实际状态来自 Agent。排队、执行中、失败、旧版本 Agent、缺少依赖和结果未明不能算作已生效。手工“读取实际状态”会让 Agent 重新核验自己的规则；状态时间表示最后一次实际检查时间，主控收到心跳不会刷新这个时间。

移除一条规则并保存，会撤销 ASWired 对该业务端口的来源限制；其他防火墙规则仍然保留。最后一条移除后，策略版本仍然保留，旧任务不能重新安装过期白名单。

## 生效边界与维护

规则按协议和业务端口生效，不随订阅用户增减变化，也不随 Xray 配置发布被清空。受保护的监听绑定不能直接改动或删除；先明确移除相应白名单，等待 Agent 确认成功，再调整监听端口并配置新的白名单。

Agent 只管理自身独立的 nftables 表，不清空整机规则。更新使用原子批处理；停止或升级 Agent 保留内核规则。重启后先恢复持久白名单，再启动代理监听；恢复失败时保留管理通道供排查，不把业务监听无保护地启动。

系统防火墙重载、管理员手工修改内核规则或其他网络组件可能改变实际状态。Agent 不在每个心跳执行 nftables 查询；维护这些组件后请重新读取实际状态并核对。此功能管理本机输入流量，不管理宿主机端口映射、Docker 转发链、商家安全组或其他网络命名空间。

启用后需备份主控数据库及 Agent 数据目录。Agent 的策略、版本与所有权记录用于恢复和防止旧任务重放；不要单独删除这些文件或手工改写 ASWired 专属表。
